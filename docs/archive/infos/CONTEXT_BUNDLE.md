# Tactical Summoners — Project Bible

**Baseline date:** 2026-10-28 | **Engine target:** Godot 4.x (exact version unverified) | **Budget:** zero-cost first

## High concept
An original persistent fantasy tactical RPG in 2D pixel art. Players summon individually generated heroes whose personalities, backgrounds and skills make them distinct; build a roster; choose a squad for tower-floor missions; and direct autonomous heroes in real time from a top-down group view. The player issues movement, target, formation and interaction orders and activates skills directly; heroes handle routine movement and combat autonomously. Missions mix combat with exploration, investigation, rescue, defense and extraction. Consequences include relationships, memories, injuries and permanent deaths. Procedural world generation is deferred/undecided and is not required for the first prototype. Inspiration is at the level of broad systems from *Pick Me Up, Infinite Gacha*, dispatch/management games and classic RTS games, not their protected expression.

## Pillars
1. Tactical preparation matters as much as raw hero rarity.
2. Procedural heroes are varied, coherent and persistent; procedural world generation is deferred until the core loop works.
3. Heroes retain identity, relationships, memories and consequences.
4. Base, economy, equipment and expeditions reinforce one another.
5. Core simulation works without an LLM or paid API.
6. Build locally first; online persistence and asynchronous social systems later.
7. Original IP only: no copied names, characters, dialogue, art, maps, logos, music or distinctive story expression.
8. Inspect existing code and preserve work before editing.

## Core loop
Open the refuge/roster → inspect generated heroes, personalities, histories and skills → choose a squad for a tower-floor mission → enter a continuous real-time top-down map → issue squad/individual orders and activate skills while heroes autonomously move, attack and react → complete the mission objective and decide whether to extract or push deeper → return with rewards, injuries, relationships and possible permanent losses → preserve the company chronicle and prepare the next expedition.

## Systems scope
- **Summoning:** configurable rarity, odds, resource cost, history, duplicate choices and stable hero IDs.
- **Heroes:** stats, class/role, skills, equipment, potential, traits, background, personality, origin and persistent history.
- **Combat and control:** hybrid RTS in real time, with no pause. Camera is a top-down view of the squad/map, not a locked single-hero camera. Heroes autonomously navigate, select basic attacks, defend themselves and use only clearly defined autonomous behaviors; player directly issues movement, attack/target, hold, follow, retreat, interact and ability commands. Direct ability use is explicit and reliable. Support squad orders and individual selection, camera focus shortcuts 1–5, group view on Tab and squad selection on G. Readable telegraphs, status effects, line of sight, navigation, aggro and retreat/extraction rules replace turn order and rank-based targeting. Hero UI shows skills, current order, vitals and compact Trust/Obedience/Composure indicators. Simulation must be deterministic and testable without rendering.
- **Consequences:** retreat, injury, permanent death, memorial/history, explicit equipment-loss rules. Never silently delete data on an error.
- **Base/economy:** training, crafting, research, storage, production, expedition board and meaningful building unlocks. Track resource sources, sinks and caps.
- **Tower/content:** floors, difficulty budgets, bosses, dungeons, missions, objectives and events. A floor is a mission space, not necessarily an arena; support combat, exploration, investigation, rescue, defense, survival and extraction. Bosses use readable phases, arena interactions and objective/mechanic changes rather than inflated HP alone.
- **Procedural worlds:** deferred/undecided. Use a fixed test dungeon/encounter sequence for the first prototype; revisit seeded regions, biomes, factions and landmarks after validating the core loop.
- **Procedural heroes (priority):** stable ID/seed, name, origin, class, attributes, growth potential, skill loadout, rarity, personality dimensions, backstory hooks, goals, fears, Trust, Obedience, Composure, relationships and memory log. See `SUMMONS_AND_HERO_GENERATION.md`. Generate from compatible data tables, validate combinations, and persist the resulting snapshot so reloads never reroll identity.
- **Relationships/memory:** structured traits, goals, bonds, rivalries, fears and event memories. LLM may phrase dialogue but must never decide rewards, inventory or game state.
- **Offline progress:** timestamp-based, capped and idempotent. Use trusted server time once online; local device time is not secure.
- **Multiplayer:** begin with cloud saves, themed player groups, visits, asynchronous defenses/invasions, leaderboards and seasonal events. Real-time multiplayer is later.
- **AI dialogue:** optional; template-based dialogue remains the free, reliable fallback. Validate output and treat player-provided text as untrusted.

## Procedural generation rules
1. Seed and version the generator.
2. Generate world profile and theme palette.
3. Generate biome/region graph, factions and tensions.
4. Generate resources, enemy families, encounters and events.
5. Assemble visuals from compatible modular assets and procedural dressing.
6. Validate navigation, combinations, difficulty and missing content.
7. Persist the generated result. Do not rely on regenerating old content using a future version of the generator.

For the first 2D pixel-art prototype, use curated sprite/portrait parts, palette variants and equipment overlays rather than generating wholly new artwork for every hero. Randomness must obey compatibility rules and visual readability. Persist part IDs and palette choices. Procedural world generation remains deferred.

## Initial original theme families
Ashen/cursed kingdom; Verdant/overgrown wilds; Arcane/fractured reality; Umbral/abyssal depths; Storm/sky-isles; Forge/clockwork empire; Tidal/drowned civilization; Crystal/glass desert. These are working labels, not final lore.

## First prototype scope (updated 2026-10-28)

- Choose a squad of five heroes from the roster (D-017). The first vertical slice also uses five; development may test one hero first, but acceptance requires five.
- At least six generated heroes in the roster; five are deployed in the initial vertical slice.
- Hybrid RTS controls: autonomous heroes plus direct orders and direct skill activation; top-down group camera; continuous real-time simulation with no pause.
- One compact fixed mission with a clear non-combat objective and at least one enemy encounter. The objective must be completable without defeating every enemy where mission design allows.
- Basic movement/navigation, autonomous basic attacks, squad movement order, keys 1–5 for hero camera focus, Tab group view, G squad selection, target/attack order, hold/follow/interact/retreat, one active skill per hero, visible Trust/Obedience/Composure, enemy detection/response and extraction/mission completion.
- Procedural hero personality, backstory, skills and persistent identity are higher priority than rarity/visual breadth.
- Permanent death with persistent memorial record; no resurrection in the prototype.
- Save/load for hero identity, stats, skills, mission outcome, equipment and memorial.
- Script-first workflow; Godot version and actual project status remain unverified.
- Procedural world generation remains deferred: use a curated fixed map for the first prototype.

## Mandatory development workflow — script-first Godot automation

**This is a standing project rule for every AI assistant, account and collaborator.** Minimize manual editor work. Whenever practical, implement project setup and repetitive Godot work through code that can be rerun, reviewed and version-controlled.

- Prefer scripts/generators for creating or updating scenes, nodes, resources, project settings, test fixtures, data files and repetitive asset setup. Use `@tool` `EditorScript`/`EditorPlugin` for editor-time generation and Godot's command-line mode for headless imports, validation and tests when suitable.
- Give the user complete, ready-to-save files or a patch with exact paths, plus the shortest possible execution steps. Do not make the user manually create many nodes or click through repetitive inspector settings if a script can do it.
- Prefer idempotent generators: rerunning them should update known generated outputs safely, not duplicate nodes or destroy user work. Before modifying existing files, inspect them and preserve unrelated changes. Do not overwrite scenes, scripts, project settings or assets blindly.
- Keep generated code readable, typed where useful, documented, modular and compatible with the project's verified Godot version. If the version is unknown, first provide the shortest way to check it and avoid relying on version-specific APIs until verified.
- Use real project files, imported asset paths, skeletons and animation names. Never invent asset paths or claim compatibility before inspection. Use a small vertical-slice test before bulk generation/import.
- After generation, provide a clear run/test command and acceptance checks. Distinguish code written from code actually executed and verified. If something fails, fix the error rather than asking the user to manually work around it.
- Manual editor work is acceptable only when it is genuinely necessary (for example, downloading assets, granting permissions, inspecting visual fit, or confirming a UI setting unavailable through code). Keep it minimal and explain why it is needed.
- Build reusable project tools over time, such as `Build Test Scene`, `Generate Hero`, `Validate Assets` and `Run Tests`, so future work becomes increasingly automated.
- This rule applies across all systems: characters, modular armor/weapons, animation setup, combat, procedural generation, UI, data, saves, testing and project configuration. It does not mean blindly generating everything; inspect, test and preserve work first.

## Technical rules
- Separate data, simulation, presentation, persistence and UI.
- Prefer script-first automation for all repetitive Godot/editor work; see the mandatory workflow above.
- Prefer typed GDScript, stable IDs and versioned save schemas.
- Keep balance tables/data out of UI scripts.
- Add tests for deterministic generation, combat, economy, offline rewards and save/load.
- Commit small increments. Record engine/plugin versions.
- Do not add paid dependencies without approval.
- No bulk asset import before a small in-engine art test.

## Out of scope initially
Real-time multiplayer, seamless open world, local LLMs, paid generative APIs, huge handcrafted campaign, monetization, mass asset production before style validation.

## Definition of done
Feature works in the real project, acceptance criteria pass, edge cases are tested, persistence is verified if relevant, documentation is updated, and all assets have compatible licenses.

# Decisions

## Current control and mission decisions (approved 2026-10-28)
- **Control model:** hybrid RTS. Heroes autonomously navigate and perform basic combat; the player gives direct orders and activates skills directly.
- **Camera:** top-down group/map view as the default. Keys 1-5 select a hero and smoothly focus/follow them (see D-015); Tab/G return to group view. The camera is never permanently locked and switching never pauses or changes orders.
- **Time:** real-time simulation with **no pause**. The UI must make orders quick to issue and readable under pressure.
- **Squad fantasy:** the intended mission squad is five heroes. Confirmed final by D-017: the first vertical slice also uses five.
- **Mission structure:** exploration and combat share the same continuous map. Missions may ask for investigation, rescue, defense, survival, recovery or extraction; defeating all enemies is not always required.
- **Hero autonomy:** direct orders should be reliable and never randomly ignored by a hidden obedience roll. Personality influences autonomous preferences, dialogue, relationships and situational behavior. If an obedience/trust system is later added, it must be transparent, context-sensitive and never undermine basic usability.
- **Boss design:** mechanics, phases, telegraphs, arena interactions and objective pressure; not simply more HP.
- **World generation:** remains deferred. Use a fixed curated map until the control and mission loop is validated.

## D-001 — Free-first
**Date:** 2026-10-27. Core gameplay must work without paid APIs, subscriptions or paid assets. Procedural generation and default dialogue are code/data based; optional AI cannot be a core dependency.

## D-002 — Original IP
Use broad genre/system inspiration, not copied protected expression. No copied characters, names, dialogue, art, maps, logos, music or distinctive story content from Pick Me Up: Infinite Gacha.

**Updated:** 2026-10-28. # Control, Camera & Real-Time Missions — Tactical Summoners

**Version:** 1.5 design baseline, 2026-10-28  
**Status:** Approved specification; not yet implemented or playtested.

## 1. Core control fantasy
The player is a field commander of autonomous, individually generated heroes. Heroes navigate, select reasonable basic-attack targets and perform routine attacks themselves. The player creates advantage by positioning the squad, choosing priorities, using active skills, issuing interactions and deciding when to extract. The game runs continuously in real time; there is no tactical pause or time-slow.

## 2. Camera modes and number keys 1–5
The default camera shows the squad and nearby map. The five number keys are dedicated hero focus shortcuts:

- Press **1, 2, 3, 4 or 5**: select the corresponding deployed hero and smoothly move the camera to follow that hero. The selected hero's portrait, status, skills and command panel become active.
- The camera keeps following the focused hero until another hero key or the group-view shortcut is pressed. This is a camera focus, not direct movement control; the other heroes continue their AI and current orders in real time.
- Press the same hero number again: recenter the camera on that hero (do not toggle into a pause or special control mode).
- Press **Tab**: return to squad/group view, framing the living deployed heroes and nearby threats. Selection remains on the last focused hero unless the player chooses a group command.
- Press **G**: select all living deployed heroes for a group order; camera returns to group view.
- If a numbered slot is empty or its hero is dead/unavailable, show a short UI message and do not silently focus another hero.
- If a focused hero moves far ahead (for example, an Explorer scouting), the camera may follow them and leave allies off-screen. Show small squad-edge indicators for off-screen allies and a quick return-to-group shortcut (Tab). Do not teleport heroes or change their orders when switching camera.
- Camera focus must never pause the simulation. Enemies continue to move, attacks resolve and objectives progress.

This resolves the intended combination: group view is the default tactical overview, while keys 1–5 let the player inspect and direct one hero at a time.

## 3. Proposed keyboard/mouse bindings
Initial bindings for keyboard and mouse, all remappable later. Do not assume final controller/mobile support until platform is confirmed.

| Input | Action |
|---|---|
| Left-click hero / portrait | Select and focus that hero |
| **1–5** | Select deployed squad slot and follow that hero with the camera |
| **Tab** | Return camera to group view |
| **G** | Select all living deployed heroes and show group view |
| Drag selection box | Multi-select heroes in visible area |
| Right-click ground | Move selected hero/selected group to location |
| Right-click enemy | Attack/mark that target for selected unit(s) |
| Right-click usable object | Interact if context is valid |
| **A** then click target/ground | Attack-move to a point or target (proposed; validate usability) |
| **H** | Hold/defend current position |
| **F** | Follow/regroup toward rally point or squad leader |
| **R** | Retreat toward active extraction point (if the mission enables it) |
| **E** or contextual button | Interact with nearby objective (proposed; avoid conflict with skill hotkeys) |
| **Q / W / E / R** | Active skills 1–4 for selected hero, only if UI and binding plan avoids conflicts; if R is retreat, use Q/W/E plus clickable skill buttons in prototype |
| Mouse wheel | Zoom camera |
| Middle-mouse drag or edge-pan | Pan camera; choose one in the first usability test |
| Escape | Close non-modal panel/clear targeting; never pauses the simulation |

**Binding note:** avoid assigning the same key to retreat and a skill. For the first keyboard prototype, use Q/W/E for up to three skills and clickable skill buttons; keep retreat on a clearly labelled UI button until bindings are playtested. The ability bar must show actual bindings.

## 4. Hero command panel (opens/updates when a hero is focused)
The hero panel is contextual and should remain readable during live combat. It contains:
1. **Identity:** name, portrait, class/role, rarity if used, level and unique ID in the detailed roster view.
2. **Vitals:** health, current resource, key conditions/status effects, injury indicator and downed/dead state.
3. **Active skills:** icon, short name, cooldown, resource cost, range and valid-target hint. Disabled skills explain why.
4. **Command controls:** Move, Attack/Target, Hold, Follow/Regroup, Interact, Retreat/Extract. Show current order state.
5. **Behavior summary:** 1–3 concise trait tags (e.g. Scout, Protective, Cautious) plus a small Trust / Obedience / Composure indicator. Full detail is in the inspect panel, not the always-on HUD.
6. **Feedback:** current order, target, path failure, skill invalidity, fear/composure event and brief combat log entries.

Selecting/focusing a hero does not stop or slow the world. UI panels must not cover the hero's immediate danger area or hide boss telegraphs.

## 5. Order model and priorities
Each hero has one primary order state:
- **Auto:** pathfind around obstacles, avoid known hazards and attack a reasonable nearby threat.
- **Move:** travel to the destination; after arrival return to Auto unless the player chose Hold.
- **Attack target:** prioritize a designated enemy. If it dies or becomes unreachable, show feedback and return to Auto or follow a documented fallback rule.
- **Attack-move:** advance toward a location while engaging reasonable threats along the route.
- **Hold/defend:** stay near a location, engage threats inside the defense radius and do not chase far away.
- **Follow/regroup:** maintain a useful distance from a leader or rally point without sprite stacking.
- **Interact:** approach and complete a contextual action with visible progress and clear interruption rules.
- **Retreat/extract:** prioritize the extraction route and avoid optional fights unless attacked or mission rules require otherwise.
- **Scout:** optional explicit order for heroes with scouting capability; move to a location, reveal/report relevant information and return or hold as configured.

Order priorities:
1. Explicit current player order.
2. Immediate avoidance of a clearly telegraphed lethal hazard, if that reaction is enabled.
3. A committed interaction/escort/defense action whose interruption rules were shown to the player.
4. Autonomous target selection and personality preferences.

New direct orders replace the previous compatible order. Do not build a complex hidden queue in the first prototype. Orders need visible destination/target markers and a reason when invalid (blocked path, out of range, target gone, cooldown, dead hero).

## 6. Autonomous behavior and individual personality
Baseline AI should be competent and predictable:
- navigate around obstacles and avoid known hazards;
- use basic attacks when no conflicting direct order exists;
- not chase targets indefinitely or abandon the active mission;
- respect direct movement, target, hold, follow and extraction orders;
- use only basic attacks autonomously in the first slice; active skills are player-triggered.

Traits alter preferences, not core input reliability. Example: an **Explorer/Scout** has greater perception, reveals points of interest sooner, gains more from investigating and may volunteer to scout when in Auto. If assigned to move ahead, the player can focus camera with key 1 (if that hero occupies slot 1), inspect the scout's skills and order them to investigate, attack, hold, regroup or extract. Other heroes continue acting under their own orders while the camera is focused on the scout.

Do not make heroes randomly refuse basic orders. Trust, obedience and composure can influence how quickly or cautiously an order is executed in special, clearly signaled circumstances, but no invisible coin-flip may cancel a routine command. See `SUMMONS_AND_HERO_GENERATION.md`.

## 7. Trust, obedience, composure and bonds in live play
- **Trust (long-term):** belief that the commander and company will protect them and treat them fairly. Influences willingness to volunteer, dialogue, recovery and relationship events.
- **Obedience (discipline):** trained reliability in carrying out orders under pressure. Primarily influences hesitation/formation discipline in extreme, telegraphed conditions—not routine order success.
- **Composure (mission state):** short-term steadiness affected by fear, injuries, isolation, allies falling and boss events. Can temporarily influence aim, reactions or skill precision if communicated.
- **Bond/rivalry (relationship):** pairwise relationship between heroes. Can trigger coordinated benefits, protective actions, conflict or post-mission scenes after validation.
- These are separate dimensions. Do not collapse them into one “morale” number. MVP stores the values and displays them but should only implement simple, deterministic effects after the base controls work.
- Any hesitation, panic or special reaction must show a clear reason and recovery path. A player command remains authoritative in ordinary situations.

## 8. Camera, HUD and no-pause readability
- Default: group framing with soft follow to group center. Hero key: camera smoothly follows that hero. Tab: group framing.
- Camera changes never affect game time, orders, pathfinding, target selection or mission progress.
- Off-screen ally indicators and danger-edge indicators are required when focusing a scout away from the squad.
- HUD layers: portraits/slot numbers, health/resource, selected hero, skill bar, order buttons, objective tracker, extraction status, enemy telegraphs, interaction prompts, Trust/Obedience/Composure mini-state and event log.
- Do not rely on color alone for selection, status or danger.
- Use camera bounds/zoom so sprites, range indicators and telegraphs remain legible.
- Commands should take one or two inputs; skills should not require a long menu sequence.
- No tactical pause, time-slow, or pause-on-skill-selection.

## 9. Mission design: exploration and combat share one map
Mission objectives may include:
- scout routes and discover points of interest;
- investigate evidence or activate mechanisms;
- rescue or escort someone;
- recover an item and extract;
- defend a location while a timer/process completes;
- survive a threat wave;
- bypass, distract or evade enemies;
- expose a boss weak point or interact with arena mechanisms;
- decide whether to extract with current rewards or continue deeper.

At least one early mission must be completable without killing every enemy. Enemies can guard routes, react to noise, interrupt objectives or chase for a bounded time. Avoid unfair omniscience.

## 10. Boss design
Use phase changes, telegraphed area attacks, vulnerable windows, arena objects, adds with a purpose, objective pressure and meaningful extraction decisions. Boss health is one tuning variable, not the whole mechanic. Every major attack must have readable warning and counterplay.

## 11. First playable vertical slice
Start with one fixed map and five heroes (D-017):
1. Roster shows at least six generated heroes; choose five for deployment.
2. Enter a top-down real-time mission with a non-combat objective and at least one enemy.
3. Press 1–5 to focus/select a hero and reveal that hero's command/skill interface.
4. Press Tab to restore group camera; verify other heroes continue acting.
5. Move, target, attack-move, hold, follow, interact and retreat/extract.
6. Activate one unique skill per deployed hero.
7. Use an Explorer to reveal/investigate a point while the rest of the team remains under AI or explicit orders.
8. Complete objective and extract while an optional enemy remains alive.
9. Save mission outcome, relationship changes and memorial/death state; reload and verify persistence.

## 12. Acceptance criteria
- Keys 1–5 select and camera-follow the correct deployed hero and update the contextual panel without pausing time.
- Tab returns to group view; G selects the group.
- Other heroes keep acting while the camera focuses one hero.
- Hero UI shows skills, cooldown/resource, current order, core status and compact social-state indicators.
- Direct orders have visible feedback and do not fail silently.
- Autonomous navigation/attacks work without constant clicking; heroes do not stack on one pixel.
- Explorer/scout can move ahead, reveal an objective and return/re-group.
- At least one mission can be completed without killing every enemy.
- Permanent death and hero relationships survive save/load.
- These are requirements, not claims of implementation; all remain unverified until tested in Godot.

# Summoning, Hero Generation & Social Simulation — Tactical Summoners

**Version:** 1.5 design baseline, 2026-10-28  
**Status:** Specification for implementation; exact balance values are provisional.

## 1. Purpose
Summoning should produce persistent people, not disposable units with a name pasted on top. Each hero has a stable identity, coherent build, personality, history, relationships and a reason to behave differently. Rarity may affect starting resources or potential, but must not replace tactical identity or make low-rarity heroes meaningless.

## 2. Core summon flow
1. Player opens the Summoning Hall and sees available summon banner/pool, cost, published odds and any guarantee/pity rule.
2. Player chooses single summon or multi-summon if supported.
3. Game validates resource cost and banner configuration.
4. Game uses a seeded, versioned random draw to select a rarity/template pool.
5. Generator creates a valid hero from compatible data tables.
6. Validation checks name uniqueness policy, class/role compatibility, stat budgets, skill prerequisites, visual-part compatibility and forbidden combinations.
7. Hero receives a stable unique ID and generation seed; final generated snapshot is saved.
8. Result screen shows rarity, portrait, role, signature traits, one-line background hook, core stats and skills.
9. Hero is added to the persistent roster. The game never rerolls their identity when reloading.
10. The player can inspect, rename only if the design allows it, equip, train, assign relationships, or deploy them to a squad.

## 3. Summon data and fairness
- Banner definitions are data-driven and versioned: ID, start/end condition, available hero pools, rarity odds, cost, currency, featured weighting and guarantee rules.
- Odds must sum to 100% and be displayed clearly before a draw.
- RNG is seeded and logged for reproducible tests. In offline single-player, local seeds are acceptable; online competitive systems later require server authority.
- A guarantee/pity system is optional. If implemented, its counter and reset rules must be visible and saved.
- Do not invent final probabilities yet. Keep them in configuration/resources, test via simulation and tune later.
- No paid API or LLM is required to generate heroes.
- If monetization is ever considered, disclose odds and avoid pay-to-win pressure. Monetization is not part of the first prototype.

## 4. Rarity is not personality
Rarity is a progression/starting-budget label, not a personality label. A common hero can have a rare combination of traits, unusual backstory, excellent team synergy or high growth potential. Rarity must not dictate obedience, trustworthiness, kindness or morality.
Suggested provisional rarity bands: Common, Uncommon, Rare, Epic, Legendary. These labels can change before content lock. Each banner has explicit odds rather than hidden per-hero adjustments.

## 5. Persistent Hero Profile
Every generated hero should store:
- `hero_id` (stable unique ID);
- `generation_seed` and `generator_version`;
- `name`, `callsign` (optional), portrait/sprite part IDs and palette;
- `rarity`, `class_id`, `role_tags`, `origin_id`;
- five core attributes: FUE, AGI, VIT, INT, TEM;
- derived stats snapshot or reproducible formula version;
- `level`, experience, growth potential, injuries and permanent-death state;
- active/passive skill IDs and skill rank;
- equipment IDs;
- personality dimensions and discrete traits;
- backstory hooks, goals, fears, preferences and personal boundaries;
- Trust, Obedience and Composure values;
- pairwise bonds/rivalries with other heroes;
- memory/event log, mission history, kills/rescues/contributions;
- current order/behavior profile only while in a mission, not as permanent identity;
- last save version and migration metadata.

Persist the generated snapshot rather than relying on the current generator to recreate it. Use data schemas and migration tests.

## 6. Personality and traits
Use a mix of bounded numeric dimensions and discrete traits. Suggested dimensions (0–100, provisional):
- **Courage:** willingness to stay engaged under danger.
- **Discipline:** follows training and formation procedures.
- **Curiosity:** notices/approaches discoveries when not under a direct order.
- **Empathy:** prioritizes rescue and reacts to ally suffering.
- **Independence:** prefers acting without constant supervision.
- **Caution:** evaluates risk and keeps distance from threats.
- **Ambition:** seeks recognition or high-value objectives.
- **Sociability:** forms bonds and communicates readily.

Do not give every dimension independent, noisy random values. Generate a coherent personality archetype, then add controlled variation and 1–3 distinctive traits. Example archetypes: Scout, Guardian, Duelist, Scholar, Survivor, Idealist, Cynic, Perfectionist. Archetypes are starting patterns, not fixed classes.

Trait examples and transparent effects:
- **Explorer:** greater perception/reveal radius; gains a bonus for investigation tasks; may suggest scouting in Auto mode.
- **Protective:** favors threats attacking a bonded ally when operating autonomously.
- **Cautious:** prefers safe approach routes and may request regrouping after a danger event.
- **Disciplined:** stronger formation keeping and faster response under pressure.
- **Independent:** more likely to volunteer for optional interactions when in Auto, but respects direct orders.
- **Curious:** finds extra clues or unique dialogue at relevant points of interest.
- **Stubborn:** may need more encouragement after a failed mission, expressed through dialogue/trust rather than refusing ordinary movement commands.
- **Brave:** lower composure loss from danger, not immunity to it.
- **Compassionate:** more affected by abandoning rescued allies; may improve rescue interactions.
- **Rivalrous:** competes with a specific hero and may create dialogue/conflict events.
- **Methodical:** interacts with mechanisms efficiently or reveals extra steps.
- **Pragmatic:** favors extraction when objective is complete and risk is high, as an advisory behavior rather than forcibly extracting.

Traits should have both narrative expression and a small number of gameplay effects. Avoid hidden effects that make the hero feel inconsistent.

## 7. Trust, Obedience, Composure and bonds
These are distinct systems and must not be conflated.

### Trust — relationship with the commander/company
- Scope: per hero, long-term, 0–100.
- Meaning: how strongly the hero believes the commander and company will protect them, keep promises and treat them fairly.
- Increases from: successful rescue, healing/support, keeping explicit promises, recovering a fallen ally, fair reward/recognition, respecting a hero's stated boundary.
- Decreases from: abandoning allies, repeatedly breaking promises, reckless orders that cause avoidable harm, unequal treatment if the game establishes fairness as a value.
- Effects: dialogue openness, volunteering, willingness to share backstory, recovery/relationship scenes, confidence during high-risk missions, and how quickly trust recovers after conflict.
- Trust must not be a simple “good person” score. Different personalities value different actions.
- Never let low trust silently lock ordinary movement, attack, interact or extraction commands.

### Obedience — command discipline
- Scope: per hero, long-term, 0–100; separate from Trust.
- Meaning: training and willingness to follow the chain of command. A trusted hero can still be impulsive; a disciplined hero can follow orders without emotional closeness.
- Increases from: training drills, clear command structure, consistent tactical doctrine, successful coordinated missions and leadership compatible with the hero's temperament.
- Decreases from: contradictory commands, repeatedly changing orders mid-action, lack of training, role conflict or leadership that violates the hero's established principles.
- Effects in MVP: visible stat, formation/command-response flavor and post-mission feedback only. No randomized order rejection.
- Later effects may include a small, deterministic response delay or more/less reliable formation keeping in extreme pressure, but the cause must be shown and basic commands remain dependable.
- Do not implement a hidden obedience chance per click. A failed command is a UI/path/target issue, not a personality dice roll.

### Composure — short-term mission state
- Scope: per hero, 0–100, resets/recovers according to documented mission/rest rules.
- Meaning: moment-to-moment steadiness under danger.
- Decreases from: being isolated, severe damage, ally down/death, ambush, boss phase shock or trait-specific triggers.
- Recovers from: safe regrouping, successful skill use, defeating a threatening enemy, support skills, rest and relevant trait effects.
- Effects: optional telegraphed states such as Shaken, Focused or Panicked at clear thresholds. MVP can show the meter without applying penalties until control is stable.
- Any state must show a warning, effect, duration/exit condition and recovery route.

### Bonds and rivalries — hero-to-hero relationship
- Scope: directed or symmetric pair records; choose one model and document it in code. Recommended MVP: symmetric relationship score plus tags for Bond/Rivalry.
- Increases/decreases through shared missions, rescues, sacrifices, conflicts, trait compatibility and remembered events.
- Effects: contextual dialogue, post-mission scenes and eventually modest combo/protection synergies.
- Do not implement random friendly fire or surprise sabotage as a relationship effect.

### Loyalty — deferred
Do not add a separate Loyalty meter in the first prototype because it overlaps with Trust and Obedience. Revisit only if the design later needs a distinct commitment-to-company system.

## 8. Relationship and memory event model
Store structured events, not just generated prose. Example:
- `event_type`: `rescued_ally`, `abandoned_ally`, `promise_kept`, `promise_broken`, `boss_fear`, `shared_victory`, `rivalry_conflict`;
- participants and mission ID;
- timestamp/mission sequence;
- stat deltas and trait tags;
- short factual summary generated from game state;
- optional dialogue template key.

The simulation decides the event and numeric changes. Optional LLM dialogue may verbalize a validated event but cannot choose outcomes, change stats, invent inventory or overwrite memory facts.

## 9. Summon duplicate policy — decision still open
Do not delete duplicate heroes automatically. Because each summon is an individual persistent character, duplicate draws should be handled by one explicit design:
- **Recommended baseline:** every draw creates a distinct hero ID; duplicate names are disambiguated with callsigns, and identical build seeds are prevented.
- If duplicates are instead converted into shards, fragments or training material, make that a deliberate player choice after the result screen and preserve the original hero if the player wants them.
- Duplicate policy and whether heroes can be released/retired must be decided before implementing the final summon economy.

## 10. Initial summon configuration (placeholders only)
Keep values in a resource/config file and mark them as tuning placeholders:
- single summon cost: `SUMMON_COST_SINGLE` (unset);
- multi-summon count/cost: unset;
- rarity probabilities: unset, must sum to 100%;
- guarantee/pity: disabled until specified;
- featured hero pool: data-driven;
- resource source/sink and duplicate conversion: unresolved.
Do not hard-code invented odds or costs into gameplay logic.

## 11. Data schema proposal
Use typed Godot Resources or JSON/ConfigFile data; exact implementation follows the verified Godot version. Suggested logical schema:
```gdscript
class_name HeroProfile
extends Resource

@export var hero_id: String
@export var generation_seed: int
@export var generator_version: int
@export var display_name: String
@export var class_id: String
@export var role_tags: PackedStringArray
@export var rarity_id: String
@export var attributes: Dictionary
@export var skills: Array[String]
@export var trait_ids: Array[String]
@export var personality: Dictionary
@export var trust: int = 50
@export var obedience: int = 50
@export var composure: int = 100
@export var bonds: Dictionary
@export var memory_events: Array[Dictionary]
@export var is_dead: bool = false
```
This is an illustrative schema, not tested code. Prefer explicit typed subresources over unvalidated dictionaries as the project matures. Clamp bounded values and validate required IDs on load.

## 12. First implementation sequence
1. Define a versioned hero data schema and stable ID.
2. Implement deterministic generator from fixed tables; no LLM dependency.
3. Generate at least six heroes with different coherent archetypes, traits, skills and backgrounds.
4. Implement summon cost/odds as configuration with odds validation; leave cost/odds unset until design decision.
5. Persist profiles and test load stability.
6. Add Trust/Obedience/Composure fields and a small event ledger; display them in the roster and selected-hero panel.
7. Apply only simple deterministic Trust/Obedience/Composure changes from scripted mission events; do not yet change core order success.
8. Implement relationships/bonds after basic persistence; add dialogue templates.
9. Later: test whether transparent personality-driven autonomy adds value without reducing player control.

## 13. Acceptance criteria
- Summoning creates a unique stable hero ID and records seed/generator version.
- Generated test heroes are observably different in role, traits, skills and backstory hooks.
- Saving and loading never rerolls identity or relationships.
- Rarity odds are visible and validated; no final odds are assumed by this document.
- Trust, Obedience and Composure are stored separately and visible in the roster/hero panel.
- A low Trust or Obedience value never randomly cancels a routine direct order.
- Mission events update the relationship ledger deterministically and can be audited.
- Dead heroes remain in the memorial and cannot be redeployed.

## 14. Synthesis, Sacrifice and Promotion (D-018)
Source of truth for hero growth through consumption and tiers. Numbers are placeholders in config, not code.

### Rules shared by all three
- Transactional: the whole operation applies or nothing does. Write a save checkpoint before it.
- Explicit confirmation screen shows exactly what is lost and gained. No hidden rolls: any randomness uses a stored seed and the result is saved.
- Hero ID, name, seed, generator version, personality and history never change. Never regenerate a hero.
- Cannot use a dead hero, a hero currently on a mission, or a hero already memorialized.
- Warn if the operation would leave fewer than five deployable heroes.
- Every operation appends structured events to the hero event ledger (`synthesized`, `sacrificed`, `promoted`, `received_synthesis`).
- Trust effects on other heroes (for example witnessing a sacrifice) are optional, deterministic and configurable; default none in the first prototype.

### Synthesis (hero -> hero)
- Input: one target hero + one or more source heroes.
- Output: target gains a portion of the sources' value (stats and/or growth potential). `synthesis_efficiency` is a config value below 1.0 and must be visibly lossy.
- Sources are retired to the memorial with cause `sacrificed` and keep identity, history and bonds.
- Open: which stats transfer, whether skills transfer, caps per target, same-class bonus.

### Sacrifice (hero -> materials)
- Input: one hero. Output: materials from a config table based on tier and class.
- Same retirement and memorial rules as synthesis.
- Open: material types, whether high-tier heroes can be sacrificed at all.

### Promotion (tier up)
- Input: one hero + promotion materials (config).
- Output: tier +1. Each tier has a data-driven unlock table: skill slot, class option, level cap, growth potential. Rarity stays separate from current power and potential.
- **Memory unlock at promotion is MAYBE** (not approved). If approved later it must reveal a structured backstory/memory entry already stored on the hero at generation time, never invent new facts.
- Materials source for the first prototype: fixed mission reward. Daily-dungeon style sources are deferred.

### Data additions to the hero profile (schema v+1)
`tier`, `promotion_history[]`, `synthesis_history[]`, `retired` (bool), `retired_cause` (`killed` | `sacrificed`), `retired_at_mission`. Add to the save format version and write a migration.

### Acceptance
- Headless tests: atomicity, reload stability, memorial entry created, invalid targets rejected, config-driven numbers, identity unchanged after promotion.

# Combat & Initial Stats — Tactical Summoners

**Version:** 1.5 design baseline, 2026-10-28. Numeric values remain provisional.

## Goals
- Make positioning, target priority, skill timing and mission objectives matter.
- Keep heroes distinct through skills, personality, history and growth.
- Make combat readable in real time without pause or excessive click speed.
- Make permanent death consequential but legible.
- Keep simulation deterministic and testable independently of rendering.

## Combat model
- Hybrid RTS, continuous real time, no pause.
- Heroes autonomously navigate and use basic attacks; active skills are player-triggered in the initial slice.
- Group camera is default; keys 1–5 select/focus the matching hero and show their contextual interface; Tab returns to group view; G selects the squad.
- No fixed combat ranks or turn order. Use world positions, movement, range, line of sight, telegraphs and cooldowns.
- Exploration, interaction, combat and extraction share the same map.
- Five heroes is the squad size (D-017), including the first vertical slice.

## Basic resolution
- Basic attacks have a configured range, wind-up, recovery and attack interval.
- Resolve attacks only if target is alive, in range and satisfies line-of-sight rules.
- Damage and mitigation are data-driven. No rank-based target restrictions.
- Show wind-up/impact feedback and health changes. Telegraph dangerous enemy actions.
- Prevent animation cancelling from creating unintended attack loops.
- Add status effects only after movement, attacks and skills work. Document duration, stacking, resistance and tick timing.
- Retreat is an explicit mission action with extraction requirements, not a free instant escape.
- Avoid critical hits, random damage variance and complex elemental interactions in the first control prototype unless testing proves they are useful.

## Skills
Initial slice: one active skill per deployed hero, activated directly from the focused hero panel or a documented hotkey. Skills may target a unit, point, area or interactable. The UI shows cooldown, cost, range, target validity and feedback. Example roles:
- Scout: reveal route / mark threats / short reposition.
- Guardian: protect an ally / intercept or shield.
- Striker: gap-close / burst damage.
- Arcanist: area control / interrupt.
- Field medic: heal / cleanse / rescue.
These are role examples, not locked classes. Skill effects should support exploration as well as combat where suitable.

## Attributes (provisional)
- **FUE — Fuerza:** physical damage and possibly stagger.
- **AGI — Agilidad:** movement responsiveness, attack speed or evasion; avoid overloading this stat.
- **VIT — Vitalidad:** maximum health and resistance to physical pressure.
- **INT — Intelecto:** skill potency and resource efficiency.
- **TEM — Temple:** resistance to fear, disruption and stress.

Do not finalize derived formulas until attack cadence, movement speed, skill scaling and encounter duration have been tested. Keep balance values in data resources/tables, not UI scripts.

## Hero autonomy and social state
Autonomous behavior is narrow in the first slice: pathfind, avoid hazards, engage reasonable nearby threats and basic attack. Direct skills are player-triggered. Explicit player orders outrank routine AI.

Trust, Obedience and Composure are separate values defined in `SUMMONS_AND_HERO_GENERATION.md`. Store and display them early, but do not implement random order rejection. For the MVP, use scripted events to adjust values; later behavior effects must be transparent and deterministic. Traits may affect preferences (e.g. a cautious hero chooses a safer route; a protective hero favors a threat attacking a bonded ally) without undermining direct control.

## Enemy design
- Melee chaser: closes distance and pressures the group.
- Ranged attacker: maintains distance and telegraphs shots.
- Controller/support: creates zones, calls reinforcements, shields allies or interferes with objectives.
Use perception and alert states rather than perfect knowledge. Noise and line of sight can alter behavior.

## Boss principles
Use phases, telegraphed area attacks, vulnerable windows, arena objects, meaningful adds, objective pressure and extraction decisions. HP is only one tuning variable. Every major attack needs readable warning and counterplay.

## Death, injury and persistence
- Permanent death; no resurrection in first prototype.
- Record death in the persistent memorial/chronicle.
- Define equipment recovery/loss and mission outcomes atomically before implementing saves.
- Save hero identity and skill snapshots; loading must not regenerate a hero.

## First-playable test targets
- The player understands a basic enemy tell and can move out of its danger zone.
- A skill changes a tactical outcome (interrupt, rescue, expose, control area or reveal).
- A mission can be completed with an optional enemy alive.
- Combat is legible at pixel-art resolution with five heroes.
- All numbers remain provisional until playtested in Godot.

# Design Gaps — Tactical Summoners

**Updated:** 2026-10-28. These are open questions, not completed features.

## Decide during the first real-time control prototype
1. **Platform/input:** keyboard/mouse first is proposed; confirm target platform before locking bindings.
2. **Pathfinding:** Godot navigation approach, collision avoidance and how heroes spread around a destination.
3. **Order semantics:** exact final bindings and when new orders replace existing orders. Current proposal: 1–5 focus heroes, Tab group view, G squad select; playtest before locking.
4. **Attack tuning:** basic attack range, wind-up, recovery, attack interval, projectile speed and line-of-sight rules.
5. **Skills:** energy vs cooldowns, per-skill targeting, interruption, cast time and whether any skills are channelled.
6. **No-pause readability:** telegraph duration, enemy warning cues, camera zoom bounds and HUD density.
7. **Survival reactions:** whether heroes auto-dodge clearly telegraphed lethal hazards; if enabled, keep it bounded and legible.
8. **Enemy awareness:** line of sight, sound/noise, alert radius and leash/chase distance.
9. **Mission completion:** exact rules for objective completion, extraction, optional enemies, failed extraction and partial rewards.
10. **Death/injury edge cases:** when death is committed to the save, equipment recovery, retreat costs and what happens if the entire squad falls.
11. **Hero autonomy/personality:** which traits affect transparent preferences; direct movement/target orders must not be randomly denied. Trust, Obedience and Composure are separate; implement data/events first, behavior effects later.
12. **Summon economy:** finalize rarity probabilities, summon cost, pity/guarantee, banner pools, duplicate policy and whether rename/release is allowed. Current document intentionally leaves numbers unset.

# Agent Sync Protocol (v1.6)

Goal: ChatGPT, Claude and other agents/accounts work on the same project without drifting apart.

## Principles
1. **Git is the memory.** Anything not committed to `docs/ai-context/` does not exist for the next agent.
2. **One owner per task.** Claims live in `TASK_BOARD.md`. Claims older than 48 h with no log entry are stale and may be taken over (note it in the log).
3. **Append-only history.** `HANDOFF_LOG.md` and `CHANGELOG.md` are never rewritten, only appended.
4. **Evidence over claims.** "Done" requires a command and result in the log.
5. **Small, file-scoped tasks.** List the files you will touch in the claim to avoid edit collisions.
6. **State hash.** `STATE_HASH` = first 12 hex chars of the SHA-256 of all `docs/ai-context/*.md` files (except the generated bundle). Any doc change changes it. Agents must state the hash they read.

## Workflows
**With shell/Git access (Codex, Claude Code, Cursor):** run `start`, work, run `log`/`release`/`check`, commit.
**Chat only (ChatGPT/Claude web):** user pastes or uploads `CONTEXT_BUNDLE.md`; agent confirms `STATE_HASH`, works, and ends with a `SESSION_END_PATCH`; user pastes it into the repo and re-runs `bundle`.
**Switching accounts mid-task:** run `log --next "exact next step"` and `release T-xxx --status handoff` before leaving; the new agent starts with `start`.

## Conflict handling
- Two agents edited the same doc: keep both changes, resolve in Git, note in `HANDOFF_LOG.md`.
- Spec vs. code mismatch: code that was run and tested wins for "what exists"; the spec wins for "what should exist". Log the gap.
- Decision disputes: add a proposed `D-xxx` marked `PROPOSED`; only the user approves.

## Commands (`tools/sync/ts_sync.py`, Python 3.8+, stdlib only)
| Command | Purpose |
|---|---|
| `start` | Show version, STATE_HASH, claims, last log entry, Git status |
| `bundle` | Build `CONTEXT_BUNDLE.md` (all docs in one file + hash) for chat-only agents |
| `claim T-xxx --agent A [--files f1,f2]` | Take a task |
| `release T-xxx --status done\|blocked\|handoff` | Free a task |
| `log --agent A --did .. --verified .. --next ..` | Append a handoff entry |
| `check` | Lint docs: versions, stale terms, links, secrets, claims |
| `install-hooks` | Git pre-commit: runs `check` and rebuilds the bundle |

# Art Direction — Tactical Summoners

**Status:** Direction selected for the first prototype: **2D pixel art**. Exact resolution, tile size and palette remain to be validated in-engine.

## Visual target
Original dark-fantasy pixel art with readable silhouettes, limited palette ramps, restrained lighting effects and clear animation timing. Prioritize gameplay readability over detail. Characters, enemies, UI icons, status effects and turn/target telegraphs must remain distinguishable at the actual game window size. Do not imitate the exact character designs, interface, icons, or visual identity of any reference work.

## First art test
Create or source with compatible licenses:
- One allied hero sprite with idle, attack, hit and death states (placeholder frames are acceptable).
- One enemy sprite with idle, attack wind-up, hit and death states.
- One small battle background or tileset sample.
- Selection rings, target highlights, range indicators and enemy telegraph icons (no rank/position markers; combat is real-time).
- A readable hero panel showing HP, resource, status effects, skills and compact Trust/Obedience/Composure markers.
- One portrait/card treatment for a hero's personality and background.

Validate sprite scale, contrast, animation readability, UI legibility, file sizes and licenses before scaling production.

## Pixel-art production rules
- Pick a working internal resolution and integer scaling only after a quick in-engine test.
- Keep palette ramps and outlines consistent across heroes, enemies, effects and environment.
- Use transparent PNG sprites/sprite sheets; document frame size, frame order, pivot/origin and animation names.
- Avoid subpixel movement where it causes shimmer; test camera and UI scaling on intended display sizes.
- Use visual telegraphs that remain clear without relying on color alone.
- Prefer modular palettes, equipment overlays and portrait variants to unique art for every procedural hero.
- Procedural variation may choose from approved sprites, palettes, equipment layers and portrait details; do not randomly splice incompatible pixels.

## Character identity through art
A generated hero's visual presentation should reflect their class, origin, equipment and a few persistent distinguishing details. The first prototype does not need a fully procedural sprite generator: curated sprite parts plus data-driven combinations are enough. Record chosen part IDs so a hero's appearance does not reroll on reload.

## World generation
Procedural world generation is deferred/undecided. For the prototype use a fixed, hand-authored battle background or small dungeon sequence. Pixel-art tile/chunk generation may be explored only after the core combat and hero loop is validated.

## Asset sourcing
Use placeholders first where practical. For each imported asset, record source, creator, exact license, attribution requirements, modification and approval status in `docs/ai-context/ASSET_MANIFEST.md`. A free download is not automatically public domain or commercially reusable.

## Avoid
- Mixing pixel art with 3D renders or smooth vector art without a deliberate conversion pass.
- Excessive detail that disappears at native display size.
- Unreadable combat effects, telegraphs or status icons.
- Random sprite combinations that cause visual mismatch.
- Copied characters, logos, UI, maps or distinctive visual expression from reference IP.


## Real-time readability requirements (added 2026-10-28)
- Pixel-art sprites must remain distinguishable at the default group-camera zoom; hero silhouettes and team selection need more than color alone.
- Telegraphs, selection outlines, target highlights, interaction points and extraction zones must remain readable against busy terrain.
- Avoid high-frequency animation or excessive screen shake that hides orders and enemy tells.
- Plan small, clear animation states for idle, move, attack wind-up, attack, hit, skill cast, stagger/downed and extraction.
- Use distinct silhouettes/weapon effects for enemy roles; boss attacks need clear safe/unsafe areas.


## Hero-focus camera and social UI readability (v1.5)
- Number keys 1–5 focus a hero while the world continues; make the focused hero unmistakable with portrait/frame/name, not color alone.
- When a hero is focused away from the group, off-screen ally edge indicators should be simple and low-noise.
- Reserve HUD space for selected hero vitals, active skills/cooldowns, order state and compact Trust/Obedience/Composure signals.
- Trust/Obedience/Composure should use icons, labels or tooltips as well as meters; do not communicate meaning through color alone.
